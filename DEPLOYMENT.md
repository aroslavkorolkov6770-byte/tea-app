# Ватэс: работа с GitHub и сервером

## Главное правило

Заливка выполняется только после прямой команды пользователя. Формулировка «залей на GitHub потом на хост» означает:

1. Сначала подготовить и отправить код в GitHub.
2. Затем обновить код на сервере.
3. Установить зависимости, если изменились `package.json` или `package-lock.json`.
4. Собрать приложение на сервере.
5. Перезапустить процесс приложения.
6. Проверить публичный сайт.

## Перед каждой заливкой

```powershell
git status --short
git diff --check
git diff --stat
```

Обязательно убедиться, что в коммит не входят:

- `data/*.json`;
- загруженные файлы пользователей;
- `.env*`;
- SSH-ключи;
- файлы с паролями, токенами, VAPID-ключами и API-ключами;
- случайные временные файлы.

## Коммит

Коммит должен быть коротким и понятным. Примеры:

- `Исправить светлую тему`
- `Улучшить навигацию по товарам`
- `Добавить сброс пароля сотрудника`

Нельзя писать расплывчатые сообщения вроде `fix`, `update`, `changes`.

## Обновление на сервере

После успешного `git push` подключиться к уже настроенному серверу по SSH и выполнить строго эту последовательность:

```bash
cd /var/www/html
git pull --ff-only
npm install
npm run build
pm2 restart tea-hub
```

`npm install` обязателен после изменения списка пакетов. Если зависимости в релизе не менялись, этот шаг можно пропустить.

`/var/www/html` - рабочий каталог сайта на текущем сервере. `tea-hub` - имя процесса в PM2. Нельзя удалять каталог приложения целиком, выполнять очистку данных, `git clean`, `git reset --hard`, копирование поверх `data/` или любые команды, которые могут удалить загруженные пользователями документы и JSON-хранилище.

## Отдельный переход production на MySQL

Обычный релиз кода не должен автоматически переключать хранилище. Пока `DATA_BACKEND=json`, сайт продолжает работать со всеми прежними JSON.

Перед первым включением MySQL:

1. Остановить административные изменения на время переноса.
2. Создать архив `data/`, список файлов и SHA-256-манифест.
3. Проверить валидность всех JSON и записать их количество.
4. Создать пустую MySQL `8.0+` базу и отдельного пользователя приложения.
5. Добавить `MYSQL_*` в защищенное окружение PM2, но оставить `DATA_BACKEND=json`.
6. Выполнить:

```bash
cd /var/www/html
npm install
npm run db:migrate
npm run db:import-json -- --dry-run
npm run db:import-json
npm run db:verify-json
npm run db:health
```

7. Только после полного совпадения переключить `DATA_BACKEND=mysql`.
8. Выполнить:

```bash
npm run build
pm2 restart tea-hub --update-env
```

9. Проверить вход, список сотрудников, профили, материалы, тесты, документы и контролируемое сохранение.
10. Повторно убедиться, что архив и исходная серверная `data/` не изменены.

Если после переключения еще не было записей, откат выполняется возвратом `DATA_BACKEND=json` и `pm2 restart tea-hub --update-env`. Если записи уже были, сначала сохранить `npm run db:export-json -- --output <отдельный-каталог>`; простое переключение на старые JSON потеряет более новые изменения.

Подробная инструкция находится в `database/README.md`.

## После обновления

- Открыть публичный сайт в браузере.
- Проверить главную страницу, вход, продукты, документы и ИИ-помощник.
- Убедиться, что данные не исчезли после перезагрузки страницы.
- При ошибке сначала сохранить текст ошибки и состояние процесса; не начинать очистку данных.

## Секреты

Секреты существуют только на защищенной машине или в защищенной конфигурации:

- SSH-ключи;
- доступ к серверу;
- ключи ИИ-провайдера;
- VAPID-ключи;
- почтовые учетные данные;
- секрет авторизации.

Не копировать их в исходный код, Markdown-файлы, коммиты, issue, PR и сообщения чата.

## Обязательная конфигурация безопасности

После локального аудита от 30 июля 2026 года production не должен запускаться
без следующей конфигурации:

```text
APP_ORIGIN=https://tea-hub.ru
AUTH_SECRET=<новое случайное значение длиной не менее 32 символов>
AI_API_KEY=<серверный ключ>
```

Допустимо использовать `NEXTAUTH_SECRET` вместо `AUTH_SECRET`. Значение нельзя
генерировать заново при каждом перезапуске: это завершит все активные сессии.

Перед первым релизом усиленной авторизации:

1. Сохранить новый секрет в защищенном окружении PM2.
2. Убедиться, что `APP_ORIGIN` точно совпадает с публичной схемой и доменом.
3. Перезапустить процесс с `--update-env`.
4. Сменить пароль администратора и потребовать смену старых паролей сотрудников.
5. Проверить вход, выход, смену пароля, административные роли и отзыв старой
   сессии.

Nginx должен самостоятельно устанавливать доверенные заголовки и не пропускать
пользовательские значения как есть:

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Если приложение запускается несколькими PM2-инстансами, встроенный лимитер
нужно заменить общим хранилищем Redis или лимитом Nginx.

Production-зависимости перед выкладкой проверяются:

```bash
npm audit --omit=dev
```

Полный `npm audit` может отдельно показывать development-зависимости ESLint.
Нельзя применять `npm audit fix --force` без проверки несовместимых обновлений.

## Перевод GitHub в приватный режим

Репозиторий сейчас публичный. До изменения видимости необходимо подготовить
доступ сервера:

1. Создать отдельный GitHub deploy key только на чтение или read-only token.
2. Настроить credential helper или SSH remote в `/var/www/html`.
3. Проверить `git fetch` и `git pull --ff-only` без интерактивного ввода.
4. Только после прямой команды пользователя сделать репозиторий private.
5. Повторно проверить pull на сервере до следующего релиза.

Нельзя сначала закрывать репозиторий, а потом разбираться с доступом: это может
остановить обновление production. Уже опубликованную Git-историю следует считать
раскрытой; секреты из защищенного окружения необходимо ротировать независимо от
смены видимости.
